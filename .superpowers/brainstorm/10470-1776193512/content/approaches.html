Three Approaches for Multi-Role Targeting

Same goal, different tradeoffs in UX depth and engineering complexity

Approach A: Role-Centric Hub Leanest

A dedicated "My Roles" hub becomes the central control plane. Each role card shows its overlay summary, linked resume variant, and skill gap score. Everything flows FROM the roles hub to other modules.

  • Roles page is the home base — primary role badge, active role indicator
  • Resume builder shows role context as a sidebar: "Building for: Business Analyst"
  • Apply flow reads active role's overlay automatically; preview in confirmation step
  • Interview prompts shown contextually ("Practice BA-specific questions?")
  • Skills module: per-role tabs + aggregate sidebar
  • Applications: primary + variant model per posting

Overlay architecture: Separate table (master bullets untouched, overlay stores custom summary + bullet priority map + keywords). LinkedIn enriches master only.

Tradeoff: Roles hub adds a new top-level concept. Existing single-role users have a new surface area to navigate. Lower engineering complexity — overlays are a new data layer, no schema migrations.

Approach B: Role-Augmented Existing Pages Recommended

No new hub. Instead, existing pages (resume, roles, apply, interview, skills) are each "role-aware" — they detect the active role and show role-specific context inline. Roles are managed from a compact settings panel or a drawer.

  • Roles page becomes richer: grid of role cards with overlay previews inline
  • Resume builder: role selector dropdown in the header ("Building for: [BA ▾]")
  • Apply flow: same recommended-with-preview as A
  • Interview: same contextual prompts as A
  • Skills module: same tabs + sidebar as A
  • Applications: same primary + variant model as A
  • New: "Role Panel" drawer (accessed from any page) — add/edit/swap active role

Overlay architecture: Same separate table model. Role panel is a global UI element (like a notification drawer) accessible from any page.

Tradeoff: More complex distributed UX (role context appears in many places). But users never leave their current page to manage roles. Higher engineering complexity — role context needs to flow through more components.

Approach C: Guided Role Journey Highest engagement potential

Roles are managed through a structured journey — not just a settings panel. After onboarding, users enter a "Role Targeting Wizard" that walks them through discovery (guided), ranking (primary selection), and overlay customization. After that, it's mostly self-directed.

  • First-time flow: Role Targeting Wizard (3 screens: discover → rank → customize overlay)
  • Returning users: "My Roles" micro-hub embedded in dashboard
  • Resume builder: role context shown as a "story selector" in the builder header
  • All other modules: same as Approach B
  • New: "Role Story" — a short description of how you position yourself for each role, generated from your overlay and used in interview prep and cover letters

Overlay architecture: Same separate table model. New "Role Story" text field on each overlay. Story is AI-generatable from overlay data.

Tradeoff: Highest upside for user engagement (the wizard creates initial investment). But the wizard adds a new flow to onboard. Users who skip the wizard end up in the self-directed mode anyway. Most engineering work.
